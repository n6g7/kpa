# Adversarial review — 2026-09

An adversarial read of the tree at commit `b40f70b`, covering two questions:
can this leak secrets, and can it crash or corrupt memory. Findings are
written to be implemented directly: each one names the location, the fix,
whether the fix belongs in this repo or upstream, and how to verify it.

Claims marked **verified** were reproduced by running code, not by reading
it. The harness pattern used is described in
[`../.claude/skills/`](../.claude/skills) — both audit skills build an
out-of-tree crate that depends on `kpa` by path, so nothing in this repo is
modified to run a check.

## Verdict on memory safety

No memory-corruption or use-after-free risk exists in this codebase.

- `grep unsafe` returns nothing in `src/` or `tests/`, and nothing in
  `keepass` 0.15.0 either. The whole path from file bytes to `EntrySummary`
  is safe Rust.
- `src/` contains no `unwrap`/`expect`/`panic!` outside test code.

The realistic failure modes are therefore **aborts, hangs, and resource
exhaustion** — not undefined behaviour. Finding 5 is a real abort; finding 1
is a real hang.

## 1. `list` silently de-protects protected fields

**Severity:** Medium — this is a leak in the one property the design
promises is not one.

**Where:** `src/vault.rs:162-176` (`collect_entries`), via
`entry.get_title()`, `get_username()`, `get_url()`.

Those getters bottom out in `keepass`'s `Value::get()`, which calls
`expose_secret()` on `Value::Protected`. A field the user marked as
protected in their KeePass client is returned as a plain `String` with no
indication that it was protected.

**Verified.** A database built with `Title`, `UserName` and `URL` all stored
as `Value::protected` yields, from `vault::list_entries` unmodified:

```
list() yielded: title=Some("SECRET-TITLE") username=Some("SECRET-USERNAME") url=Some("SECRET-URL")
```

This contradicts two standing claims: the doc comment at `src/vault.rs:96-98`
("No password, no notes: `list` is an index, never a secret dump") and
`docs/design.md:145` ("**`list` never returns secrets** — it is an index").
Both are true of the *password* field and false of any other field the user
chose to protect. `docs/design.md` also routes `list` to every client over
the socket, so this is not confined to `probe`.

**Fix (this repo).** Decide the policy explicitly rather than inheriting it
from a convenience getter. Preferred: have `collect_entries` read fields
through an accessor that checks `Value::is_protected()` and omits the value,
returning `None` (or a redaction marker) for protected fields, so the index
stays an index. Whatever is chosen, make `EntrySummary`'s doc comment state
it, and reconcile `docs/design.md:145`.

**Verify.** A regression test constructing an entry with a protected
`UserName` and asserting `list_entries` does not return its plaintext. This
needs no fixture file — build the `Database` in-process.

## 2. The master password is never zeroized

**Severity:** Medium — cheap now, expensive to retrofit once `server.rs`
exists.

**Where:** `src/main.rs:63`, and the signature at `src/vault.rs:116-120`.

`rpassword::prompt_password` returns a plain `String`. **Verified:** version
7.5.4 contains no `zeroize` anywhere — the password is accumulated
character-by-character in an internal buffer that is also dropped unwiped.
`probe()` then holds that `String` and drops it without clearing it.

`docs/design.md:235` claims "Master password | No — zeroize immediately
after key derivation", justified by `DatabaseKey` implementing `Zeroize` and
`Drop`. That is true of the library's *copy* — `DatabaseKey` does derive
`ZeroizeOnDrop`, and the `DatabaseKey` built in `vault::open` is moved into
`Database::open` and dropped there — but it is not true of the original that
came out of the prompt.

`vault::open(password: Option<&str>)` is what forces this: `&str` cannot
carry a zeroizing guarantee, so every caller is pushed into holding a plain
`String`.

**Fix (this repo).**

1. Add `zeroize` as a direct dependency (it is already in the tree via
   `keepass`; making it direct is intentional, not redundant).
2. Change `vault::open` to take the password as `Option<&Zeroizing<String>>`
   (or a `SecretString` newtype) rather than `Option<&str>`. The `&str`
   handed to `DatabaseKey::with_password` is then produced at the last
   moment, inside `open`.
3. Wrap the prompt result: `let password = Zeroizing::new(rpassword::prompt_password("Password: ")?);`

Note that step 3 alone does not fix it — `rpassword`'s own internal buffer
is still unwiped, so a residual copy survives regardless. Step 3 removes the
copy this codebase is responsible for, which is the part that is in scope.
Mention the remaining `rpassword` copy in the code comment so it is not
mistaken for a complete fix.

**Fix (`docs/design.md`).** Amend row 235 to say what is actually true: the
key material held by `DatabaseKey` is zeroized on drop; the prompt's own
buffer is outside kpa's control.

## 3. `lock` does not remove plaintext from the process

**Severity:** Medium. **Fix lives:** split — part here, part upstream, part
in the doc.

**Verified** by scanning the process's own writable mappings, with the
scanner fully pre-allocated so it does not churn the heap it is measuring:

```
[while unlocked]
          "entrypass1" -> 1 copies      (the entry password)
 "https://example.com" -> 3 copies
               "alice" -> 3 copies
[AFTER the Database is dropped (== what `kpa lock` will do)]
          "entrypass1" -> 0 copies      <- SecretBox did its job
 "https://example.com" -> 2 copies      <- still there
               "alice" -> 3 copies      <- still there
```

The `secrecy::SecretBox` path works: protected values are gone after the
drop. Everything else is not. Three sources, in descending size:

1. **Upstream.** `keepass` decrypts the payload into a plain `Vec<u8>` and
   decompresses into another (`format/kdbx3.rs`, `let xml =
   compression.decompress(&buf)?`; the KDBX4 path is equivalent). Neither is
   zeroized — `zeroize` appears in only four places in that crate, and none
   of them is the plaintext XML. This is the largest residue and it is **not
   reachable from this codebase**: `Database::open` owns those buffers
   start to finish.
2. **Upstream.** The inner-stream cipher's plaintext output is a `Vec<u8>`
   that is dropped unwiped before the value reaches `Value::protected`.
3. **This repo.** `EntrySummary`'s `String` fields are ordinary heap
   allocations, freed without clearing.

`docs/design.md:202` ("Locking means: drop the `Database`, zeroize what can
be zeroized") and the Security table at `:238` together read as *lock clears
the decrypted database*. It does not.

**Fix (this repo).** Zeroize what is ours: make `EntrySummary`'s string
fields zeroize on drop (`#[derive(Zeroize, ZeroizeOnDrop)]`, or store
`Zeroizing<String>`). This is a small share of the residue but it is the
share this repo is responsible for.

**Fix (upstream).** Wrapping the two decrypted buffers in `Zeroizing` is a
small, self-contained patch to `keepass`. Worth filing regardless of whether
it is waited on.

**Fix (`docs/design.md`).** This is the important half. State plainly that
locking drops the database and zeroizes key material and protected values,
but that decrypted plaintext may persist in freed heap pages until the
allocator reuses them. Leaving the current wording in place claims a
property the program does not have.

**Verify.** The heap-residue scan is reproducible and belongs in the
security-audit skill rather than the test suite — it depends on allocator
behaviour and would be flaky as a test.

## 4. Parser text is forwarded into user-facing errors

**Severity:** Low today, structural later.

**Where:** `src/vault.rs:91` (`VaultError::Corrupt(other.to_string())`),
surfaced at `src/main.rs:49` (`eprintln!("error: {err}")`).

The library's error text can embed raw content from the decrypted database.
**Verified** instance in `keepass`'s `cs_bool` deserializer:

```rust
Err(serde::de::Error::custom(format!("Invalid boolean string: {}", s)))
```

`s` is the element's text, straight out of the decrypted XML. Today the
fields reachable this way are structural (`enable_auto_type`,
`enable_searching`, `is_expanded`) rather than secret, and the only sink is
`probe`'s stderr — hence Low.

It is worth fixing now because `docs/design.md` already plans `detail`
strings travelling back to clients over the socket, and a daemon will
eventually log.

**Fix (this repo).** Establish the rule while there is one call site:
library parser text never crosses a process boundary. Keep the detail for
developers behind an explicit debug path, and give `Corrupt` a fixed,
content-free message for anything user- or client-facing. A comment on the
`Corrupt` variant stating the rule is as valuable as the code change.

## 5. Unbounded recursion in `collect_entries`

**Severity:** Low (not currently reachable from a file), but it is the only
way this repo's own code can abort the process.

**Where:** `src/vault.rs:162-176` — `collect_entries` recurses once per
group nesting level.

**Verified** stack overflow, with lower thresholds than expected:

```
depth  4000,  2 MiB stack -> survived
depth  8000,  2 MiB stack -> stack overflow, aborting (exit 134)
depth 65535,  8 MiB stack -> stack overflow, aborting (exit 134)
```

2 MiB is `std::thread`'s default stack, which is what the planned daemon's
connection handlers will get. Stack overflow aborts the process; it is not a
panic and `catch_unwind` does not help.

**Reachability.** Not currently reachable via KDBX3/KDBX4: quick-xml 0.42
caps deserializer nesting at 128, verified by opening a 2000-deep vault —

```
error: database file is malformed or corrupt: Error parsing XML inside KDBX:
XML is too deeply nested, recursion limit of 128 exceeded
```

However `Database::parse` also dispatches legacy KeePass 1.x `.kdb` files to
`parse_kdb`, which builds the group tree *iteratively* from a `u16` level
field with no depth cap and no XML layer in the way. That path was read from
source, not exercised end-to-end, so treat reachability as plausible rather
than demonstrated. The overflow itself is demonstrated.

The point stands either way: the safety of this function currently rests on
an undocumented limit inside a transitive dependency.

**Fix (this repo).** Replace the recursion with an explicit worklist:

```rust
fn collect_entries(root: keepass::db::GroupRef<'_>, out: &mut Vec<EntrySummary>) {
    let mut stack = vec![root];
    while let Some(group) = stack.pop() {
        for entry in group.entries() { /* ... push EntrySummary ... */ }
        stack.extend(group.groups());
    }
}
```

Note this changes traversal order from depth-first-preorder to something
else; if order ever matters to a client, push children in reverse. It does
not matter today (`list` is an unordered index) but say so in a comment.

**Verify.** A test that builds a 100_000-deep group tree in-process and
calls `list_entries`. This needs no fixture file and fails loudly (abort) on
regression.

## 6. A corrupt file is indistinguishable from a wrong password

**Severity:** Low, UX-shaped, but it compounds finding 7.

**Where:** `src/vault.rs:48-49` (the message) and `:86-88` (the mapping).

Two distinct conditions converge on `WrongCredentials`: KDBX3's
`InvalidPadding` (the reasoning in the comment at `:73-85` is correct and
worth keeping), and a KDBX4 file whose header has been modified, which fails
the header HMAC and surfaces as `IncorrectKey`.

So a corrupted or modified vault tells the user they mistyped. The natural
response is to retype the password — repeatedly, into a key derivation whose
cost is read from the file being retried (finding 7).

**Fix (this repo).** Reword to admit both possibilities, e.g. `"wrong
password or keyfile, or the file has been modified"`. Keep the existing
comment explaining why the two cannot be told apart — that research should
not be lost.

## 7. Corrupt KDF parameters hang the unlock instead of erroring

**Severity:** Low. **Fix lives:** mostly upstream.

`.kdbx` files are user-controlled in practice, so there is no meaningful
attacker here. What remains is the accident case, which is real.

**Verified.** The KDBX3 header carries `TransformRounds` as a bare `u64`
and has no integrity check over it at all (KDBX3 stores its header hash
*inside* the ciphertext). Setting it to `u64::MAX` — an 8-byte edit —
produces an unlock that never returns:

```
TransformRounds was 1000000 -> 18446744073709551615
$ timeout 20 open(fixture)
exit=124   # still spinning at 100% CPU
```

`keepass`'s AES-KDF is `for _ in 0..self.rounds { ... }` with no ceiling.

**This was hit by accident, not by construction.** A byte-mutation run over
the KDBX3 fixture — 1 to 16 random byte flips per iteration — wedged on
iteration 58 and was still inside a single `vault::open` 90 seconds later. A
clean open of that fixture takes 21 ms. The `TransformRounds` field is ~0.4%
of the file, so a hit arrives every few dozen mutations, and any flip in its
high bytes means ≥2^55 AES rounds. Ordinary corruption — a truncated sync, a
bad sector, a half-written copy — is sufficient.

With vault access serialized behind a single `Mutex` (`docs/design.md`
§ Concurrency, rule 4), one such file wedges every database, not just its
own.

The KDBX4 equivalent is worse in kind but not in reachability: its header
SHA-256 is keyless, so it does not survive corruption either, and the
Argon2 memory parameter is applied *before* the HMAC that would reject the
file. A 4 GiB value produces `memory allocation of 4294967296 bytes failed`
and SIGABRT — an abort, not a `Result`, and not catchable.

**Fix (upstream).** Ceilings on `rounds`, `memory` and `parallelism` inside
`keepass` before the KDF runs. This is where the fix belongs.

**Fix (this repo), if the daemon's availability matters enough.** kpa could
pre-parse the header — it is plaintext TLV plus a VariantDictionary, roughly
80 lines — and reject implausible parameters before calling
`Database::open`. The cost is a second, partial KDBX header parser to keep
in step with the real one. That is a genuine maintenance burden for a
low-severity fault; recommendation is to file upstream, add a comment at
`src/vault.rs:116` recording the hazard, and revisit only if it is hit in
practice.

A timeout around the unlock is *not* a complete mitigation: a Rust thread
cannot be cancelled from outside, so a hung KDF keeps burning a core even if
the caller stops waiting, and the KDBX4 allocation abort takes the whole
process down regardless of which thread it happens on.

## What is solid

Worth recording, because the README's disclaimer is more pessimistic than
the code deserves:

- The error taxonomy in `src/vault.rs` is unusually well-constructed, and
  the `InvalidPadding` investigation at `:73-85` is the kind of thing that
  normally gets assumed rather than verified against the actual library.
- `default-features = false` on `keepass` means `save_kdbx4` is off, which
  gives the "read-only is structural" claim a real second leg beyond the
  `Request` enum. Worth a comment in `Cargo.toml` so it is not casually
  re-enabled; a test asserting no write path exists would be better still.
- No `unsafe`, no panics in `src/`, `?` throughout.

## One correction to `docs/design.md` § Security

`:249` — "zram swap (RAM-backed, compressed) means key material cannot be
paged to disk, and `mlock` buys nothing on top of that" is too strong.
Hibernation, a zram writeback device, and any secondary disk-backed swap all
defeat it, and it is a property of the machine rather than of kpa. An
in-process `mlockall` is a claim kpa can make about itself; zram is a claim
about someone's configuration. The `PR_SET_DUMPABLE=0` decision is right and
under-sold — it also blocks same-uid ptrace regardless of
`kernel/yama/ptrace_scope`.

## Addendum — the lock path after step 2

A scoped re-check of finding 3, now that a daemon exists: does `lock`
(`src/server.rs`, `impl Lock for Server`, which drops the `Database` by
setting its slot to `None`) clear the decrypted database?

**Verified**, through the real `Server` rather than `vault` alone, with the
same pre-allocated scanner as finding 3. Results were identical across
repeated runs:

```
without a `list` request first
needle                      before  unlocked  after LOCK
entrypass1 (protected)           0         1           0
alice                            0         3           2
https://example.com              0         3           2
Example (title)                  0         3           2

with one `list` request served before the lock
needle                      before  unlocked  after list  after LOCK
entrypass1 (protected)           0         1           1           0
alice                            0         3           5           4
https://example.com              0         3           4           3
Example (title)                  0         3           5           4
```

**Protected values: cleared.** `Value::Protected` is a `secrecy::SecretBox`
(`keepass` `db/types/value.rs:15`), which zeroizes on drop. Finding 3's
result still holds.

**Unprotected values: not cleared, and step 2 doubled the residue.**
`Value::Unprotected(T)` is a plain `String` and neither `Value`, `Entry` nor
`Database` implements `Drop`, so two copies per unprotected field survive the
lock from `keepass` alone — finding 3's upstream share, unchanged. Serving a
single `list` adds roughly two more that also survive. Those are this repo's
(**reasoned** attribution, by elimination: `EntrySummary` zeroizes on drop,
so the survivors are the next two copies on the path):

> **Corrected** by `docs/review-2026-09-secrets.md` finding 5, which
> measured each copy separately: the survivors are the serialized JSON
> buffers, not the `WireEntry` clones. The attribution below was reasoned
> by elimination and got the first item wrong. Both are now zeroized
> regardless.

1. **`WireEntry`** (`src/proto/list.rs`) — plain `String` fields, built by
   cloning out of `EntrySummary` in `server::wire_entries`. That function's
   comment argues cloning "costs nothing security-wise that sending them
   wouldn't already"; that is true of the socket and false of the heap.
2. **The serialized response** — `serde_json::to_string` in
   `server::handle_connection` produces a plain `String` holding every
   entry's title, username and URL.

Every `list` served while unlocked leaves another round of these, so the
residue after a lock grows with how much the daemon was used.

**Severity:** Low–Medium. Nothing crosses a boundary it shouldn't; this is
residue in freed heap, readable only by something that can already read
the process's memory. But `docs/design.md` § Lock policy says lock "clears
what it can", and for these two copies it doesn't.

**Fix (this repo).** Zeroize what is ours:
- `#[derive(Zeroize, ZeroizeOnDrop)]` on `WireEntry` (`#[zeroize(skip)]` on
  `uuid`), matching `EntrySummary`.
- Serialize the response into a `Zeroizing<Vec<u8>>` sized exactly up front
  — measure with a counting writer first — so the buffer never reallocates
  and leaves an unwiped predecessor behind.

This brings the post-lock count back to `keepass`'s two, not to zero.

**Fix (the doc).** `docs/design.md:246` and its footnote at `:254` describe
the master password as arriving through `rpassword` in `main.rs`. It no
longer does: the daemon runs the configured `prompt` command and reads its
`output.stdout`, a plain `Vec<u8>` that is not zeroized. The scan above did
not find the master password at any point, but a clean scan here is
allocator luck, not a guarantee — the footnote should name the new residual
copy instead of the old one. `rpassword` itself is now an unused dependency
in `Cargo.toml`.

**Verify.** Re-run the scan with `list` served before the lock; the
"after LOCK" column for unprotected fields should drop from 4 to 2.
